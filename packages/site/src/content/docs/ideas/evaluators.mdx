An evaluator gets the document that it evaluates, and the parts of that document, as data. It decides when to evaluate each part, and in which context. A condition evaluates only one branch. A sequence evaluates its steps in order. A handler keeps its run until the event comes.

## The rule

An evaluator can do three things with a part:

- Evaluate it, in a context that the evaluator chooses.
- Give it to another evaluator.
- Keep it as data for later.

It must not look inside the part to decide what to do.

## Why the rule matters

When no evaluator looks inside its parts, two parts that give the same answers can replace each other in each place. This gives a simple test for a new evaluator: run the old evaluator and the new evaluator on the same documents, and compare each answer. When the answers agree, the new evaluator can replace the old one.

The theory has a result for the other case. If an evaluator can examine the text of its parts, two programs are interchangeable only when they are written identically.

## Editors are different

An editor, a checker or a compiler works on the document as data. It must look inside. These tools work before evaluation or beside it. They do not give meaning to a document, thus the rule does not apply to them.

## An evaluator is a document

An evaluator is not one fixed formula language. A pure evaluator can be a formula. An evaluator of effects is a sequence of calls. An evaluator that builds a tree is a tree template. Each evaluator is written in the language that fits its side. Code evaluators stay as the base cases.
